behind the user interface @ Dynamicland

If you came into Dynamicland for the first time and you had to label what we were doing, it would be totally reasonable to guess that we were researching "tangible user interfaces". But I wouldn't describe our work that way.

The problem isn't at all with the "tangible" part. Tangibility is great – Dynamicland is all about physicality, materiality, spatiality, embodiment. The problem is with the "user interface" part.

In some sense the word "interface" is totally generic. It's just whatever you interact with. But in practice, in the year 2019, the word carries heavy connotations.

Interfaces are made by designers. When users use interfaces, they are bound by the decisions made by these designers. The interface isn't an optional tool the user can put aside when it's not helpful. It's a barrier. The user can neither see nor change anything lying behind it.

What lies behind the interface?

  • There's all the information the computer has (labelled here as INFO).
  • And there's all the processes the computer performs (labelled here as CODE).

In the modern world of computing, the world of web apps and mobile apps and VR apps, users have access to nothing behind the interface.

With tangible user interfaces, the situation potentially gets even worse. The information and code are even further from users than they are in a traditional computer.

That's because, while the user and their interface lie in the tangible, physical world, everything that's running the show lives on a computer somewhere, in an extremely intangible world.

What we're trying to make at Dynamicland is the opposite of that. Rather than making interfaces, or a tool for building interfaces, we want to make a system like paper, which you can freely read and write and fold into a sailor hat. That's one way to understand what we mean by "medium". Rather than making "tangible user interfaces", we're trying to make a "tangible dynamic medium".

(As a point of comparison: If you're looking at a website on a laptop, there's this nice coincidence, which is that the person who made the website made it on their laptop, so maybe you can open up Developer Tools and peer a teeny bit behind the curtain. But people who make tangible interfaces are not making them using tangible interfaces. The gap between creator and consumer grows wider and wider.)

So we want to pull the information and code into the tangible side, to make them part of the tangible medium.

And while we're at it, let's just get rid of that clunky old interface and that "user" designation.

And with all that extra space, let's give our little friend a couple more friends they can enjoy this medium with!

Nice.

Roughly speaking, that's what we're trying to pull off at Dynamicland. We're trying to replace the shallow interface with a deep medium. We are extremely not there yet, but I'd like to show you some steps we've taken in that direction, pulling information and code over to the tangible, empowering side.

I'll talk about code first.

How do we get people up next to code, in the tangible world?

The first step to doing this is really simple…

We print it out! Here's a little gadget a friend made at Dynamicland which does some stuff with tokens you put on these pages. These pages have code printed on them. I'm gonna zoom in on that "Dot counter" page.

That code you see there is, in fact, the code that's detecting the three little tokens on the page, and drawing circles around them. In fact, nothing is running in Dynamicland except the code on visible pages. If you flip over a page, the code stops running.

So with printing, code becomes visible and tangible. Next we make it modifiable.

At the same time, using traditional textural code is not really taking advantage of the rich materiality and spatial affordances of the physical world. Also, traditional code is not the best way to learn how to code.

We have a lot of ideas for how to make programming something you do with physical objects. You should be able to express programs in hand-drawn diagrams, by stacking blocks together, or by acting out examples. We've just begun to really push on this. I'm putting up one recent prototype without any explanation, to tease you and encourage you to chat with me about this if you're interested.

But let's move on to the other thing usually hidden behind the interface curtain: information! When I say "information", I mean lots of things. An email is information. So is a row in a table. So is the setting of a dial on a machine.

When we talked about making code tangible, the challenge was just getting it into the physical world. That's not an issue here. Information was tangible long before it was virtual. Books! Photographs! Card catalogs! Board games! There's really no end to the list.

The challenge is now a more subtle one. How can we use these physical media as part of our computer system, without losing the speed and flexibility of computers?

As a case study: Here's a project the staff made together. It's called the Research Gallery. Different projects people have worked on are arrayed across the wall as cards. When you point a laser at one of the cards, a description, images, and videos come up at the top of the wall.

For instance: Here's the card that represents Paula's Utility Kit. Here, at the top of the WALL, are the details about that project that come up after someone lasers the card.

Clearly, there's information here. In particular, each project has information associated with it: title, description, images, etc. Ordinarily, this would call for a database. But a database is intangible. This means it's invisible by default, and unmodifiable by default. If you want to see or change it, you need to build a special interface.

So we decided that instead of a database, we would store the information in a scrapbook.

The scrapbook sits on a table in front of the gallery sofa, so you can leaf through it. Each page represents a different project

Here's the page for Paula's Utility Kit. It has scraps on it with all of that information you saw at the top of the wall: description, date, images, videos, etc.

Once Paula made this page, she snapshotted it into the card she put on the wall. The snapshot stores all the information it needs to display the stuff at the top of the wall when it's lasered.

I am very excited about this technique. For one thing, we get to replace a database with a beautiful, decorate-able scrapbook. For another, we don't need a designer-built, opaque interface to connect a photo to a page; we just need a glue stick.

So we can assemble physical objects into books, storing information. But computers don't just take information in from people; they sometimes deliver it back to them. How can a computer control a physical arrangement? Here's a demo of one approach:

It's fun to startle people with the Dragglebot. Also, it points toward something which will become more and more important over time: if the physical world is going to be the substrate for computational information, eventually people and computers are both going to need to be able to move things around. That means we'll need some serious robotics.
